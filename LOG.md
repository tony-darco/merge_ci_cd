## [M0] `kubectl apply` rejects the Argo CRDs — annotation too large
- Symptom: `kubectl apply -n argo -f manifests/argo-install/quick-start-minimal.yaml` created most resources fine, but errored on all four large CRDs (`workflows.argoproj.io`, `workflowtemplates.argoproj.io`, `clusterworkflowtemplates.argoproj.io`, `cronworkflows.argoproj.io`) with `metadata.annotations: Too long: may not be more than 262144 bytes`. `workflow-controller` then crash-looped since its own CRDs didn't exist.
- What I assumed: the vendored manifest (pinned to the same v4.1.1 as the installed `argo` CLI, fetched straight from the GitHub release) would apply cleanly with plain `kubectl apply`.
- What I tried: nothing else first — the fix was known on sight (Argo's auto-generated CRDs are large enough that `kubectl apply`'s client-side `last-applied-configuration` annotation blows past Kubernetes' 256KiB annotation limit; this is a known issue with big CRDs generally, not specific to this manifest).
- Root cause: `kubectl apply` (client-side) stores the entire applied manifest as a JSON annotation on the object for future 3-way diffs. Argo's CRDs carry huge OpenAPI schemas and exceed that annotation's size cap.
- Fix: re-ran with `kubectl apply --server-side -n argo -f manifests/argo-install/quick-start-minimal.yaml`, which uses server-side field management instead of the annotation and has no such size limit. All 8 CRDs installed; `workflow-controller` recovered on its own after a couple of restarts once its CRDs existed.
- Time lost: ~5 minutes.

## [M0] Sandboxed browser tool refuses the Argo UI's self-signed HTTPS cert
- Symptom: `argo-server` serves HTTPS by default with a self-signed cert. `curl -k` reaches it fine (200), but the Claude Code browser pane's `navigate`/`preview_start` both silently failed ("navigation ... denied or failed") with no way to click through a cert warning — headless/sandboxed browser automation doesn't offer the "proceed anyway" interstitial a human gets.
- What I assumed: registering the URL in `.claude/launch.json` (the documented way to preview a localhost server) would be enough regardless of TLS.
- What I tried: `preview_start` with a raw `url`; then `.claude/launch.json` pointing at the same `https://localhost:2746` — both failed identically, confirming it's the cert, not the discovery mechanism.
- Root cause: the sandboxed browser has no interactive path to accept a self-signed certificate.
- Fix: patched `argo-server` to serve plain HTTP instead — `kubectl patch deploy argo-server --type=json -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--secure=false"}]'`. That alone left the rollout stuck, because the readiness/liveness probes still probed `https://:2746/` and never went Ready against a now-HTTP server; had to also patch `readinessProbe.httpGet.scheme` to `HTTP`. `--secure=false` is a fine tradeoff for a local demo cluster behind a port-forward, not something to carry into any real deployment.
- Time lost: ~10 minutes.

## [M0] Can't parameterize `resources.limits.memory` with a workflow parameter
- Symptom: `argo submit ... --parameter memory-limit=256Mi` failed immediately with `Failed to parse workflow error="quantities must match the regular expression '^([+-]?[0-9.]+)([eEinumkKMGTP]*[-+]?[0-9]*)$'"`, before the workflow ever reached the cluster.
- What I assumed: `{{workflow.parameters.memory-limit}}` inside `resources.limits.memory` would get substituted like any other Argo template variable, the same way `{{workflow.parameters.image}}` worked fine in the container's `image` field.
- What I tried: nothing else — the error message plus knowing Kubernetes resource quantities are a strictly-typed field pointed straight at the cause.
- Root cause: `resources.limits.memory` is a Kubernetes `resource.Quantity` field, which the workflow CRD's schema validates against a strict regex at parse time — *before* Argo's own `{{...}}` template substitution runs. The literal string `{{workflow.parameters.memory-limit}}` doesn't match that regex, so parsing fails before the parameter is ever resolved. `image` worked because container image is a plain string field with no such format constraint.
- Fix: stopped trying to parameterize the quantity at all. Split `sample-pipeline.yaml` into two templates — `test` (default resources) and `test-oom-limited` (hardcoded `memory: 16Mi`) — and pick between them with `argo submit --entrypoint`, which only sets which template runs (a plain string) and has no such validation problem.
- Time lost: ~5 minutes.

## [M0] `argo submit --wait -o json` prints the pre-completion object, not the final status
- Symptom: `argo submit ... --wait -o json` correctly blocked until the workflow finished (confirmed via a separate plain-text `argo submit --wait` run showing `Failed at ...`), but the JSON it printed had `status: {startedAt: null, finishedAt: null}` — no `phase` key at all, so `workflow["status"]["phase"]` raised `KeyError`. Separately, `--wait` also makes the CLI exit non-zero whenever the *workflow* fails, which isn't a script error for these deliberately-broken seeds — had to stop using `check=True` for this call too.
- What I assumed: `-o json` combined with `--wait` would print the fully-resolved final workflow object, the same one `argo get -o json` returns afterward.
- What I tried: ran `argo submit --wait` without `-o json` first to confirm the workflow really was reaching a terminal `Failed` state (it was, in ~10s) before concluding the JSON output itself was the stale part, not the wait behavior.
- Root cause: `argo submit -o json`'s JSON appears to reflect the object as constructed at submission time, not re-fetched after `--wait` unblocks — a CLI quirk, not a controller/status problem.
- Fix: split into three steps instead of one: `argo submit -o name` (submit, get the bare name back immediately), `argo wait <name>` (block until terminal phase), `argo get <name> -o json` (fetch the real final object). More calls, but each does one thing and actually returns what it claims to.
- Time lost: ~10 minutes.

## [M1] `format: "json"` alone isn't enough -- qwen3.5's "response" comes back empty
- Symptom: `POST /api/generate` with `{"model": "qwen3.5:0.8b", "prompt": ..., "format": "json", "stream": false}` returned `"response": ""` -- completely empty -- while the model's actual (garbled, not-valid-JSON) output showed up in a separate `"thinking"` field instead.
- What I assumed: `format: "json"` alone would be enough to get clean structured output back in `response`, the same way it's documented to work for non-reasoning models.
- What I tried: compared against a plain-text prompt first to confirm the model was reachable and responding at all (it was) before suspecting the JSON-mode interaction specifically.
- Root cause: `qwen3.5` is a hybrid reasoning ("thinking") model. By default it streams its reasoning into `thinking` and only puts a final answer in `response` once it decides it's done thinking -- and under strict JSON-mode constraints it apparently sometimes never produces that final answer, leaving `response` empty.
- Fix: added `"think": false` to the request body. With thinking disabled, `response` came back as clean, directly-parseable JSON (`{"ok": true}`) on the same prompt. `providers/ollama.py` sends `think: false` on every structured-output call.
- Time lost: ~10 minutes. Directly confirms the spec's §7.7 warning about small local models and structured output -- and is a concrete data point for how the Triage fallback ladder (DECISIONS.md #16) earns its keep.

## [M2] Diagnosis's `affected_files` came back as an absolute path, silently producing a whole-file-add diff
- Symptom: a live end-to-end diagnosis+fix run against `code-defect` produced a *correct* fix (removed the erroneous `/ 100`) but a garbage diff: `@@ -0,0 +1,5 @@` -- the whole file added as new, instead of a 1-line change.
- What I assumed: `DiagnosisResult.affected_files` would always come back relative to the repo root (e.g. `src/sample_app/discounts.py`), matching what an earlier manual test run had actually produced.
- What I tried: printed `diagnosis.affected_files` directly and found `/Users/tdarco/Documents/Projects/merge_ci_cd/sample-app/src/sample_app/discounts.py` -- an absolute path this run, where a prior run on the same fixture had returned a relative one. Non-deterministic model output, not a one-off fluke to shrug off.
- Root cause: `fix.py`'s `_read_relevant_files` looked up `checkout_path / rel_path` using the path exactly as the Diagnosis LLM returned it. An absolute path doesn't match anything under `checkout_path`, so the file read silently returned nothing, `old_content` defaulted to `""`, and `difflib.unified_diff("", full_new_content)` correctly-but-uselessly described that as "add everything."
- Fix: two layers, not one. (1) Tightened the Diagnosis prompt to explicitly ask for paths "relative to the repo root, exactly as they'd appear in a git diff (e.g. `src/sample_app/discounts.py`), never absolute." (2) Added `_normalize_path()` in `fix.py` as a defensive normalizer regardless of what the prompt asks for -- searches for a `src/` or `tests/` anchor in the path string and keeps everything from there, so an absolute path (local or from a container's `/app/...` layout) still resolves correctly. Prompting alone isn't a fix per spec §7.7; the code has to tolerate the model not listening.
- Time lost: ~15 minutes.

## [M2] Diagnosis pointed at test files, not the source file -- Fix Agent hallucinated a whole-file rewrite it couldn't have gotten right
- Symptom: `run_fix_agent.py --seed code-defect` "succeeded" (both guards passed) but the written diff was `@@ -0,0 +1,8 @@` -- claims to *create* `src/sample_app/discounts.py` from nothing, with a hallucinated function signature (`original_price, discount_percent` instead of the real `amount, pct`). That diff cannot `git apply` cleanly against a checkout where the file already exists.
- What I assumed: `DiagnosisResult.affected_files` would name the actual source file implicated in the root cause, since that's what "affected_files" should mean.
- What I tried: printed the diagnosis output directly and found `affected_files: ['.../tests/test_pricing.py', '.../tests/test_discounts.py']` -- this run, Diagnosis named the *test* files that detected the bug, not the source file that caused it. A different, real, non-deterministic diagnosis than the one two runs earlier that correctly named `discounts.py`.
- Root cause: `fix.py`'s file retrieval only reads `diagnosis.affected_files` plus test files pattern-matched from `FAILED ...::` log lines -- neither path led to `discounts.py` this run, so the Fix LLM was never shown the file it was "fixing" and had to invent one from scratch, informed only by the test assertions. It produced plausible-looking, functionally-reasonable logic, but as a diff it's fiction -- it doesn't know it's replacing 5 real existing lines.
- Fix: don't trust `affected_files` as the only signal. Added `_infer_source_files_from_test_imports()` in `fix.py`: scans the failing test files' own `from <pkg>.<module> import ...` statements and resolves each to `src/<pkg>/<module>.py`, adding any that exist on disk to the retrieval set regardless of what Diagnosis named. Also tightened the Diagnosis prompt to ask specifically for "the source file(s) implicated in the root cause, not the test file(s) that merely detected it" -- belt (better prompt) and suspenders (retrieval no longer solely dependent on the model getting that instruction right).
- Time lost: ~20 minutes. This is the sharpest concrete argument yet for why the spec insists on sandboxed verification before any PR: a confidently-produced, guard-passing diff was still substantively wrong.

## [M3] Verification container hung, then failed, on a real fix diff -- two compounded bugs, not one
- Symptom: `docker run` of the verification image with `patch.diff` mounted hung for 30-60s across two attempts with no output. After adding `--batch` to the `patch` invocation (to rule out an interactive prompt) and rebuilding, the hang became a fast failure instead: `patch: **** malformed patch at line 7` / `can't find file to patch at input line 3` / `No file to patch. Skipping patch.`
- What I assumed: initially, that `patch` itself was hanging waiting on stdin (plausible pre-`--batch`, since an unresolvable "which file?" prompt with no tty would block forever). After the `--batch` fix, I assumed the new fast failure was a real `-p1` strip-level bug in the patch's path headers vs. the container's file layout.
- What I tried: (1) `docker exec`/`kill` on the hung container, `git worktree prune -v` to inspect state. (2) A direct debug run overriding `--entrypoint /bin/sh` to manually step through `mkdir`/`cp -r`/`cd`/`patch` with output streamed live, no `set -e`, no backgrounding -- this surfaced that the debug run's OWN `git worktree add` had ALSO failed first (`fatal: ... is a missing but already registered worktree`), meaning `/workspace/src` may have been mounted from empty/stale content rather than a real checkout, confounding the patch diagnosis. (3) Fully cleared the stale registration (`git worktree remove --force`, `git worktree prune -v`, `rm -rf`), recreated `/tmp/verify-checkout` from scratch, and *confirmed* (`ls`, `cat discounts.py`) it held real, correct seed-branch content this time -- then a plain host-side `patch -p1 --forward --batch --dry-run` against it succeeded cleanly, proving the `-p1`/path-header theory was wrong and the entire earlier failure chain was stale-worktree noise: an empty/missing mount has nothing to patch, hence "can't find file to patch," and (pre-`--batch`) hence the original hang waiting on an unanswerable prompt.
- Root cause: two independent bugs, discovered in sequence. (1) A leftover `git worktree` registration at `/tmp/verify-checkout` from an earlier interrupted cleanup meant every subsequent `git worktree add` to that path silently failed, so the container's read-only mount pointed at empty/stale content -- not the fresh checkout the debug session assumed. (2) Once genuinely fresh, the patch STILL failed inside the container specifically (not on the host): GNU `patch` (installed via `apt-get` in the Debian-based image) rejected the diff as "malformed" / "unexpectedly ends in middle of line," while macOS's bundled BSD `patch` had silently accepted the exact same file. Root cause of *that*: `fix.py::_unified_diff_for()` fed `difflib.unified_diff()` an LLM-generated `new_content` string that didn't end in `\n` (the model's JSON response simply hadn't included a trailing newline), producing a diff whose last line has no newline character and no `\ No newline at end of file` marker -- a technically-malformed unified diff that one patch implementation tolerates and the other doesn't.
- Fix: three changes. (1) Cleaned up the worktree properly (`git worktree remove --force` + `git worktree prune -v` before ever reusing a path) and re-verified freshness by reading real file content back, not just checking the command's exit code. (2) `_unified_diff_for()` now normalizes both `old_content` and `new_content` to guarantee a trailing `\n` before diffing, regardless of what the model returned -- the diff format itself no longer depends on an LLM detail neither guard nor prompt was checking for. (3) `verify/entrypoint.sh` no longer runs under `set -e`: a failed `patch` now writes `{"tests": {}, "patch_applied": false}` to `results.json` and exits 0, so the host side gets an explicit, parseable "the patch didn't apply" result instead of a container that dies silently before writing any output (which is what made this hard to debug in the first place -- the earlier `set -e` entrypoint gave no signal to distinguish "patch failed" from "container crashed" from "still hung").
- Time lost: ~50 minutes, across two separate sessions of this conversation.

## [M5] Step 0's Ollama-from-a-pod check "failed" -- but the assumption it was written to test actually holds
- Symptom: `kubectl run ollama-check --image=curlimages/curl -- curl http://192.168.1.17:11434/api/tags` from inside a fresh k3d pod timed out after 8s (`HTTP 000`). Read at face value, this is exactly the k3d pod->LAN routing failure decision #33 predicted, and would mean fixing routing before any other M5 work.
- What I assumed: that the timeout meant what it looked like -- k3d's Docker bridge network (172.18.0.0/16) not routing out to the LAN (192.168.1.0/24), the documented k3d failure mode the step was written to catch.
- What I tried: isolated the layers instead of accepting the first plausible explanation. (2) General internet egress from a pod (`curl https://api.github.com`) -- **HTTP 200**, so egress works in general; the problem was specific to that address. (3) The same request from the macOS host itself -- **also failed**, in 1ms with "Couldn't connect to server". That's the tell: if the host can't reach it either, it isn't a container-networking problem at all. (4) To be sure LAN routing genuinely works from containers rather than merely inferring it, started a throwaway `python -m http.server` on the host's own LAN IP (192.168.1.107) and hit it over **TCP** from both a node container (`OK`) and a pod (`HTTP 200`) -- ICMP ping alone wouldn't have proven TCP works, so this was worth doing properly.
- Root cause: the Ollama host at 192.168.1.17 is down again -- the same external outage that interrupted M4, not a k3d networking problem. The two failure modes looked different (1ms "couldn't connect" from the host vs. an 8s timeout from the pod) purely because of where NAT sits in each path, which is what made the container-side symptom so convincingly look like a routing bug.
- Fix: none needed for routing -- **k3d pod->LAN TCP routing is confirmed working**, so decision #33's assumption holds and no `--network`/host-alias workaround is required. The real constraint is availability of the external Ollama host, which is outside this project.
- **Update, once the Ollama host came back:** re-ran the exact same check -- `kubectl run ollama-check --image=curlimages/curl -- curl http://192.168.1.17:11434/api/tags` from inside a fresh k3d pod -> **HTTP 200**. Decision #33's assumption is now confirmed positively, not just inferred from the TCP-to-192.168.1.107 proxy test: k3d pod->LAN routing works, no `--network` flag or host alias needed, and the original timeout was entirely the external host being down.
- Time lost: ~10 minutes, and worth every minute: this is precisely why decision #33 put the check at step 0. Had it run at step 11 instead, the identical symptom would have surfaced *after* RBAC, the sandbox namespace, and the exit hook were all written, and the natural instinct would have been to suspect the NetworkPolicy I'd just authored (decision #32) rather than an unrelated external host being down -- a far more expensive false trail. Note the check did NOT confirm what it was written to suspect; it disproved it, which is just as useful an outcome.

## [M5] The sandbox NetworkPolicy "didn't work" -- it did; short-lived pods race the enforcement sync
- Symptom: with `sandbox-egress-allowlist` applied (DECISIONS.md #32), a throwaway pod in `agentic-fixer-sandbox` still reached `https://api.github.com` and got **HTTP 200**. Retested after several minutes in case of propagation delay -- still 200. Then tested a non-allowlisted *in-cluster* target (`httpbin.argo`) to see whether enforcement worked intra-cluster but not for external traffic -- also 200. On the face of it, the sandbox isolation this milestone depends on was pure fiction: declared in YAML, enforcing nothing.
- What I assumed: that k3s/k3d wasn't enforcing NetworkPolicy at all -- either the controller was disabled, or (the version I half-expected) kube-router's egress support was too limited to honor the policy, meaning I'd need a different isolation mechanism entirely.
- What I tried: worked down the stack instead of swapping mechanisms on a hunch. (1) Policy is registered (`kubectl get networkpolicy`) -- yes. (2) k3s started without `--disable-network-policy` -- confirmed via `docker inspect` on the server node's args. (3) Netpol machinery live -- 80 `KUBE-NWPLCY`/`KUBE-ROUTER` iptables chains present on the agent node. (4) Dumped the actual programmed rules: my policy was translated *correctly* on both nodes, with the right ACCEPT rules for DNS/53 and minio/9000 and the right jumps from `FORWARD`/`OUTPUT`. So the policy was real, correct, and installed -- yet not matching. (5) That left the match criteria themselves: the rules match on `-m set --match-set KUBE-SRC-... src`, so I dumped that ipset -- **`Number of entries: 0`**. Empty. No traffic could ever match, so everything fell through to allow.
- Root cause: kube-router populates a policy's source ipset from the pods it observes, and that sync is not instantaneous at pod start. Every test pod I'd used was ephemeral -- created, ran one `curl`, exited within ~10-20s -- and finished *before* its IP was ever added to the ipset. The policy was never being evaluated against those pods at all. Re-tested with a long-lived pod (`sleep 300`), waited ~25s, confirmed the ipset populated (`Number of entries: 1`, the pod's IP on both nodes), then `kubectl exec`'d the same three requests: public internet **blocked**, non-allowlisted in-cluster `httpbin` **blocked**, allowlisted minio **HTTP 200**. The policy works exactly as designed.
- Fix: none needed to the policy itself -- it's correct. What changed is the *test*: verifying a NetworkPolicy with a short-lived pod is an unsound method that reports a false pass, so the M5 exit check now uses a long-lived pod, waits for the ipset to populate, and only then exercises the three cases. Also note this cuts the other way and is the more interesting half: **there is a real enforcement race at pod startup**, and the verification workflow's pods are themselves short-lived (a `pytest` run is seconds). So a sandbox workload can, in principle, egress freely during its first moments before the policy binds to it. That's a genuine limitation of this isolation approach, not a hypothetical -- recorded here and flagged as an M7 hardening item rather than quietly left in a milestone whose whole point is that the sandbox is locked down.
- Time lost: ~25 minutes, and it nearly cost far more: the obvious reading of "HTTP 200 from inside a deny-by-default namespace" is "this mechanism doesn't work, pick another one," which would have meant discarding a policy that was correct all along and rebuilding isolation on something else. The plan's exit check was deliberately worded as "confirms egress is *actually* denied, not just declared in YAML" -- it caught the right thing, and then the naive version of that same check turned out to be what was lying.

## [M5] Exit hook fired but `run-agent` crashed on literal, unsubstituted `{{workflow.parameters.*}}` text

Reproduced the same call locally against the live workflow instead (worked fine), then in-pod under the real ServiceAccount via `kubectl run --overrides` (also worked fine), which localized the failure to the hook invocation specifically rather than the code or the identity. Then noticed the controller configmap has `archiveLogs: true`, so `argo logs <workflow>` could retrieve the archived output of the deleted pod -- which handed over the exact traceback.
- Root cause: `{{workflow.parameters.X}}` resolves against the **calling workflow's own** `spec.arguments.parameters`, not against arguments passed to a `templateRef`. `image` and `commit-sha` substituted correctly precisely because they *are* real parameters on `sample-pipeline`; `workflow-name` and `namespace` existed only as hook arguments, so nothing resolved them and Argo passed the raw `{{...}}` strings straight through rather than erroring.
- Fix: use the built-in `{{workflow.name}}` / `{{workflow.namespace}}` variables directly in the `run-agent` template, which always resolve and -- inside a hook -- refer to the pipeline workflow being diagnosed, which is exactly the intended target. The redundant `workflow-name`/`namespace` hook parameters were then deleted rather than left as decoration.
- Time lost: ~20 minutes, most of it retrieving the traceback rather than fixing the bug. Worth noting Argo does not fail loudly on an unresolvable `{{...}}` -- it silently forwards the literal text, so the error surfaces far downstream (here, as a confusing `kubectl` failure) rather than at template validation.

## [M5] The carefully-scoped RBAC wasn't being applied at all -- pods ran as `default`
- Symptom: with the hook finally working end-to-end, `run-agent` still logged `warning: kubectl logs failed ... User "system:serviceaccount:argo:default" cannot get resource "pods/log"`. The workflow nonetheless reported `Succeeded` and reached the correct verdict.
- What I assumed: that `spec.serviceAccountName: exit-handler-sa` on the `run-agent-wft` WorkflowTemplate governed the pods it produced -- and I had *verified* that SA's permissions carefully with seven `kubectl auth can-i` checks, all correct.
- What I tried: nothing lengthy -- the error names the offending identity outright. The `auth can-i` checks had all passed, so the grants were right; what they could never show is whether that identity was the one actually in use.
- Root cause: a `templateRef` borrows **templates only**, not workflow-level `spec` fields. Invoked as a hook, the referenced template's pods inherit the *calling* workflow's service account, which was the namespace `default` SA. So the scoped identity this milestone's whole security story rests on was never in play; the pods ran with whatever `default` happened to have.
- Fix: declare `serviceAccountName: exit-handler-sa` on each **template** (`fetch-source` and `run-agent`), not only at `spec` level. Re-ran: the Forbidden warning is gone and the run is clean.
- Time lost: ~10 minutes. The lasting lesson is about the *verification*, not the fix: `kubectl auth can-i --as=<sa>` proves a grant exists, and proves nothing whatsoever about which identity a pod actually assumes. Both checks are needed, and only the second would have caught this. It also passed a full end-to-end run while broken -- `infra-failure`'s signal lives in the node's `message` field, not pod logs (DECISIONS.md #22), so the one permission that was missing happened to be the one this seed doesn't need. A green result was actively concealing a misconfigured security boundary. M7's RBAC audit should assert the running pod's identity, not just the grant table.

## [M5] Triage refused a real bug live -- the 0.8B model is only 67% accurate, and the fallback ladder never fires
- Symptom: the first full live hook run on `seed/code-defect` completed cleanly and returned `RESULT: refused at triage -- category=CONFIG_OR_SECRET`. Wrong: this seed is a plain assertion failure, and the identical fixture had classified as `CODE_DEFECT` every time during M1-M4. The model's stated reasoning cited "a failed file signal handler due to context cancellation" -- Argo executor preamble, not the pytest output underneath it.
- What I assumed: that the live log must differ from the M0 fixture -- extra Argo executor noise, truncation, or interleaved wait-container output -- and that cleaning the captured log would fix the classification.
- What I tried: diffed the two directly instead of assuming. The live log and the fixture log are **byte-identical in length (2423 chars)** and structurally the same, Argo preamble and all -- the fixture was captured from an equivalent real run at M0, so there was no discrepancy to clean. That ruled out the data and left the model. So I measured rather than guessed: 12 runs of `run_triage` on the same fixture -> **CODE_DEFECT 8/12 (67%), FLAKY 4/12 (33%)**, all twelve verdicts produced by `qwen3.5:0.8b`. Then 8 runs of the same prompt against `qwen3.5:latest` -> **CODE_DEFECT 8/8 (100%)**.
- Root cause: two compounding things. (1) `qwen3.5:0.8b` is simply not reliable at a six-way classification -- a third of runs are wrong on the project's own running example. (2) More importantly, the fallback ladder (DECISIONS.md #16) is wired to `SchemaValidationFailure`, so it only rescues *malformed* output. Every wrong answer here was perfectly schema-valid, just semantically wrong, so the ladder never engaged once in 12 runs. The mechanism guarded the failure mode that is easy to detect and missed the one that actually matters.
- Fix: escalate on *consequence*, not just on parse failure (DECISIONS.md #34). Getting `CODE_DEFECT`/`DEPENDENCY_ISSUE`/`FLAKY` wrong is recoverable -- all three route onward into real work, and `FLAKY` self-corrects outright, since the retry reproduces a genuine bug and the graph proceeds to Diagnosis anyway. A terminal refusal is not recoverable: the run simply ends, and a fixable failure is silently dropped. So `run_triage` now re-checks with the stronger model whenever the primary returns a terminal category that no deterministic detector corroborated, and the trace records why it escalated. This keeps the cheap model on the common path (escalation costs a second call only on refusals) while removing the unrecoverable failure mode. Two tests cover it: escalation on an uncorroborated refusal, and *no* escalation on a self-correcting category (so the cost saving is real, not incidental).
- Time lost: ~30 minutes, most of it measuring rather than fixing -- and the measurement was the valuable part. The single observed misclassification looked like bad luck; the honest answer is that this had roughly a 1-in-3 chance of happening on any run and had simply not come up across M1-M4. Worth stating plainly: decision #16 predicted the small model would struggle and built a ladder for it, but guarded the wrong failure mode, so the safeguard had never once fired in practice.

## [M5] Three more failures between "verification submits" and "verification works"
Grouping these: each was a distinct root cause, found in sequence once `ArgoVerifier` could actually submit workflows into the sandbox.

**(a) `FileNotFoundError: 'argo'` -- the implementation contradicted its own decision.**
`ArgoVerifier._submit` shelled out to `argo submit --from workflowtemplate/...`, but decision #26 had deliberately kept the argo CLI *out* of the agent image, and the Dockerfile comment even says so. Worked locally (argo on PATH), died instantly in-pod. Fixed by submitting a plain `Workflow` object with `spec.workflowTemplateRef` via `kubectl create -f -`, which is precisely what `argo submit --from` does underneath. Lesson: a decision recorded in DECISIONS.md is not self-enforcing -- the code drifted from it within the same milestone, and only the in-cluster run caught it, because the developer machine happened to satisfy the assumption the image did not.

**(b) `artifact driver test not found` -- artifact repository config is per-namespace.**
All submitted verify workflows errored immediately. The controller-level `artifactRepository` in `workflow-controller-configmap` is a `plugin: {name: test}` driver that does not exist. Workflows in the `argo` namespace work only because the quick-start manifest also installs an `artifact-repositories` ConfigMap *there*, annotated as the namespace default, carrying a real s3/minio config. A brand-new namespace has no such ConfigMap and falls through to the broken controller default. Fixed by giving the sandbox namespace its own `artifact-repositories` ConfigMap plus a copy of the `my-minio-cred` secret. Worth noting the secret is copied at setup time with a documented `kubectl` one-liner rather than committed to the repo.

**(c) `failed to look-up entrypoint/cmd for image ... UNAUTHORIZED` -- emissary can't introspect a local-only image.**
The verify template relied on the image's own `ENTRYPOINT`. Argo's emissary executor resolves an unspecified command by querying the *registry*, which 401s against Docker Hub for `agentic-fixer-verify:base` -- an image that exists only via `k3d image import` and was never pushed anywhere. Fixed by stating `command: ["/usr/local/bin/verify-entrypoint.sh"]` explicitly in the template. This one is specific to local-image workflows and would never appear with a registry-hosted image, which is exactly why it is worth recording.

## [M5] The sandbox's network isolation worked -- and that is what broke the test run
- Symptom: with artifacts and images finally resolved, all four sandbox verify workflows reported `Succeeded`, yet the agent concluded `unresolved after 2 fix attempt(s) -- 4 failed -> 4 failed, 0 passed -> 0 passed`. Only 4 results, none passing, where the baseline should be 5 failed / 9 passed across 14 tests.
- What I assumed: that the source artifact had arrived incomplete or in the wrong layout, since "0 passed" smells like nothing being importable.
- What I tried: pulled the workflow's `results` output parameter -- four entries, all keyed by *module* (`tests.test_discounts`) rather than by test id, which is the shape a **collection error** produces, not a test failure. That pointed at import time rather than assertion time. The container logs then gave it away outright: `ERROR: Could not find a version that satisfies the requirement setuptools>=68 (from versions: none)` / `Failed to build 'file:///workspace/run' when installing build dependencies`.
- Root cause: `verify/entrypoint.sh` ran `pip install -e .`, which triggers a PEP 517 build that fetches `setuptools` from PyPI. The sandbox namespace's egress allowlist (DECISIONS.md #32) permits DNS, minio, and the API server -- and nothing else. So pip could not reach PyPI, the editable install failed, `sample_app` was never importable, and all four test modules failed at collection. **The isolation did exactly what it was built to do**; the verification step simply had a network dependency nobody had noticed, because under Docker it silently succeeded against the host's internet access.
- Fix: drop the editable install entirely and set `PYTHONPATH=/workspace/run/src` instead. The sample app is a src layout, so this makes it importable with no build step, no download, and identical behavior under both verifiers -- and the Docker suite got faster as a side effect (17.5s -> 4.4s), since it had been doing a pointless reinstall on every run. Widening the allowlist to include PyPI was considered and rejected: allowing a sandbox that executes model-authored code to reach the public package index would undo most of the point of the sandbox.
- Time lost: ~15 minutes. This is the most instructive failure of the milestone: an isolation boundary is only proven at the moment something legitimate trips over it, and the "green" Docker path had been quietly depending on unrestricted internet the whole time.

## [M6] The first real PR opened fine and was quietly misleading -- wrong base branch
- Symptom: `--open-pr` worked end-to-end on the first try and opened a genuine PR. Inspecting it as a reviewer would, the diff was `+3/-1` and read as a pointless refactor: it introduced an intermediate `result` variable and a stray blank line, with no bug fix visible anywhere.
- What I assumed: nothing yet -- I only caught this because I looked at the rendered PR rather than trusting that "PR created, tests green" meant the artifact was right.
- What I tried: `gh pr view --json` plus `gh pr diff`. The base was `main`, and the head was the seed commit plus the fix. Since `main` never contained the bug, GitHub was correctly showing me the difference between *fixed seed* and *a branch that was already fine* -- which is a stylistic delta, not the fix.
- Root cause: `BASE_BRANCH` defaulted to `main`. But the PR has to target the branch that actually failed, and in this project that is `seed/<name>`. Basing on the project default is wrong in general, not just here: a real CI fix targets the branch whose commit broke, not trunk.
- Fix: thread the failing branch through as `base_branch` -- `run_orchestrator` already knows it (`seed/<seed>`), so it flows into graph state and on to `gh pr create --base`. `main` survives only as a fallback for callers that genuinely cannot say. Re-ran: the new PR bases on `seed/code-defect` and shows `+1/-1`, exactly `- return result / 100` / `+ return result`. Closed the first PR with a comment explaining why rather than silently deleting it.
- Time lost: ~10 minutes. Worth stating plainly: every automated check passed on the misleading PR. Guards check the diff, verification checks behavior, and neither has any notion of "is this the right thing to show a human." The only thing that caught it was opening the artifact and reading it -- which is exactly the review step decision #6 insists on, applied to the tool itself.

## [M6] The PR body claimed isolation it did not always have
- Symptom: not a crash -- caught while reading the rendered body. The Verification section stated "Run in an isolated sandbox with no network egress" unconditionally, and the disclaimer said the suite "passed in an isolated sandbox".
- Root cause: that sentence is true of `ArgoVerifier` and flatly false of `DockerVerifier`, which runs on the developer machine with full network access -- and the PR I had just opened was produced by the Docker path. On top of that, even the Argo claim is stronger than what the sandbox actually delivers, given the enforcement race logged above: the egress policy lands shortly *after* pod start.
- Fix: `_verification_environment_note()` now reports the environment that actually ran -- Docker says plainly that it is **not** network-isolated, Argo describes the default-deny policy *and* discloses that a very short-lived pod may predate enforcement. The fixed disclaimer no longer mentions sandboxing at all and points at that section instead. A test asserts each branch, including that the Docker body never claims "default-deny egress" and that the Argo body never drops the race disclosure.
- Time lost: ~5 minutes. This is the failure mode this project is supposed to be most careful about: the system was overstating its own guarantees in the one document a human uses to decide whether to trust it. An honest PR body that says "this ran unsandboxed" is far more useful than a reassuring one that is wrong.
